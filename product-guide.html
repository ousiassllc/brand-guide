案件ガイドの作り方

プロダクトをまたいで同じ見た目の形式にするための手順書です。共通ガイドが骨格を決め、プロダクトが決めてよいのはここに書いた範囲だけ。トークンの実体は tokens.json / tokens.css / theme.css にあり、そのまま写して使えます。

1. 共通と案件の切り分け

プロダクトの数が増えても「同じ家族に見える」ことを保つため、変えてよい場所を狭く固定します。

区分対象誰が決めるか
面と文字--ink --bone --mute --surface --border共通（変更不可）
状態色--success --warning --danger --info共通（変更不可）
プリズム--prism-* 5 色共通（ロゴ・KV 専用。UI 禁止）
フォーカス--focus共通（変更不可）
形・間隔角丸 --r-*、余白 --s-*、間隔レシピ --gap-*共通（変更不可）
書体Sora / Noto Sans JP / JetBrains Mono、サイズスケール共通（変更不可）
動き--motion-* --ease-*共通（変更不可）
骨格ブレークポイント、--z-*、アイコン（Iconoir）共通（変更不可）
狭い面外側の余白・ナビの形（部品の寸法は変えない）共通（狭い面の節）
アクセント--accent --on-accent --accent-soft案件（宣言すれば変更可）
テーマライト／ダークの提供範囲案件（理由を書けば単一可）
拡張トークンそのプロダクトにしかない意味の色・寸法案件（派生元を明記）
独自ウィジェット地図・判定バッジなど案件固有の部品案件（共通ガイドに発明しない）
共通の変数を上書きしないでください。足りないときは拡張トークンとして別名で足し、派生元の共通トークンを案件ガイドに書きます。共通側を直したいときは 6. 共通への戻し方 を通してください。

2. トークンの配り方

値の正は tokens.json。CSS はそこから build-tokens.mjs が生成します。各プロダクトは生成物を写して持ち、写しが原本と一致することを検査します。

ファイル形使うところ
tokens.jsonJSON値の正。Figma の変数・スクリプト・CSS 以外のスタック
tokens.css素の :root ＋ [data-theme=dark] ＋ prefers-color-schemeTailwind を使わないビルド（Outlook の作業ウィンドウなど）
theme.cssTailwind v4 の @themeTailwind v4 を使うプロダクトの本体

写し方

写しは専用のディレクトリに置き、一切編集しません。製品の上書きは隣の別ファイルに書きます。こうすると「写しを直してしまった」が起きません。

vendor/ousiass-tokens/theme.css   <- 原本の写し。編集禁止
src/styles/accent.css             <- このプロダクトの上書き（3 変数だけ）
src/styles/app.css                <- 上の 2 つを読む
/* app.css */
@import "tailwindcss";
@import "../../vendor/ousiass-tokens/theme.css";
@import "./accent.css";

/* accent.css — 案件ガイドに宣言した 3 変数だけ */
@theme {
  --color-accent: #xxxxxx;
  --color-on-accent: #xxxxxx;
  --color-accent-soft: #xxxxxx;
}

一致の検査

  • 写しの先頭には版（Ousiass 共通 UI トークン v1.0.0）が入っています。案件ガイドにもその版を書き、ずれたら気づけるようにします
  • 各リポジトリに nightly の job を置き、公開中の原本と写しを diff します。差が出たら Issue を立て、取り込むかどうかを判断します
  • PR のたびに取りに行かないのは、外部への通信で CI を落としたくないためです。写しはコミットされているので、ビルドはネットワークに依存しません
# nightly の中身
curl -fsSL https://ousiassllc.github.io/brand-guide/theme.css -o /tmp/upstream.css
diff -u vendor/ousiass-tokens/theme.css /tmp/upstream.css
原本側（この リポジトリ）では node build-tokens.mjs --check が tokens.json と CSS の食い違いを落とします。CSS を手で直さないでください。

3. 製品 accent の決まり

共通ガイドの既定の --accent はインク色（#050505）です。プロダクトは、識別のためにこれを 1 色だけ差し替えられます。

差し替えてよい変数

変数役割要件
--accent主ボタンの地・現在地・タブの下線・進捗の充填--bone と --surface の両方に対して 3:1 以上（非文字の UI 部品の境界として）
--on-accent--accent の上に載る文字・アイコン--accent に対して 4.5:1 以上
--accent-softホバー・選択・現在地の地この上の文字は --ink。--ink に対して 4.5:1 以上

ライトとダークの両方を出すプロダクトは 3 変数 × 2 テーマ = 6 値を決めます。単一テーマなら 3 値です。

使ってよい場所

  • 主ボタンの地（--on-accent の文字と組で）
  • ナビの現在地・タブの下線・選択状態
  • 進捗バーの充填、スイッチの ON
  • テキストリンク（下線と必ず併用）
  • アイコンの「強調したい 1 つ」だけ

使ってはいけない場所

  • 本文・見出しの文字色（--ink を使う）
  • ページやカードの地（--bone / --surface を使う）
  • 成功・注意・エラーの表現（状態色を使う）
  • アイコンの既定色（--mute / --ink）
  • フォーカスリング（共通の --focus 固定）
  • 1 画面に 2 色目のアクセントを足すこと

--accent-soft の作り方

アクセントをその場の地に 10〜14% 混ぜた値を基準にします。彩度を上げた別の色を持ってこないでください。

/* ライト */
--accent-soft: color-mix(in srgb, var(--accent) 12%, var(--surface));
/* ダーク（地が暗いので混ぜる比率を少し上げる） */
--accent-soft: color-mix(in srgb, var(--accent) 18%, var(--surface));

固定値で持つ場合も、上の式から外れすぎない値にしてください。--accent-soft の上に --accent の文字を置かない（コントラストが足りません）。

ダークの作り方

  • ライトの --accent をそのままダークで使わない。暗い地の上では沈みます
  • 色相は保ったまま明度を上げる（Material のトーン 40 → 80 に相当）
  • --on-accent は反転して同系の暗い色にする。白のままだとコントラストが落ちます
  • 無彩色の地（#050505 / #141414）に対して 3:1 以上を実測で確かめる
プリズムを製品 accent にしないでください。 プリズムの 5 色はロゴとキービジュアル専用です。--prism-blue と --focus が同じ値なのは、フォーカスリングに限って借りているためで、accent として使ってよいという意味ではありません。

4. テーマの決まりと例外

原則はライト・ダークの両方です。ただし、ダークを出さないほうが素直な面があります。

単一テーマにできる条件

次の 3 つをすべて満たすときに限り、案件ガイドに書いたうえでライトのみ（またはダークのみ）にできます。

  • 表示面が OS のテーマに追従できない、または追従する意味が薄い（滞在が短い小さな面、埋め込み、印刷物向けなど）
  • 案件ガイドに理由と再検討する条件を書く（「どうなったらダークを入れるか」）
  • 共通ガイドのダーク値を否定しない（将来入れるときは共通の --ink / --bone / --surface のダーク値をそのまま使う）
「工数が足りない」は条件になりません。それは未対応であって例外ではないので、案件ガイドではなく課題として残してください。

5. 案件ガイドに必ず書くこと

各プロダクトのリポジトリに置く案件ガイドの最小構成です。共通ガイドの内容は写さず、リンクします（写すと必ず古くなります）。案件ガイドは短いほどよい——長いということは、共通にすべきものが案件に溜まっているということです。

節書くこと
0. 位置づけ共通ガイドの URL と、この文書が決めるのは差分だけであること
1. 製品 accent3 変数の値（ライト／ダーク）と、コントラストの実測値
2. テーマ提供するテーマ。単一なら理由と再検討の条件
3. トークンの写し写しの場所と、取り込んでいる共通トークンの版
4. 拡張トークンそのプロダクトにしかない色・寸法と、派生元の共通トークン
5. 独自ウィジェット共通ガイドにない部品の一覧と、使ってよい画面
6. 共通との既知の差まだ揃っていない項目の短い一覧と、その製品だけの事情。ここが空なら完全準拠
改訂履歴いつ・何を・なぜ変えたか

1 節の書き方（ひな形）

| 変数           | ライト   | ダーク   | 実測コントラスト            |
| -------------- | -------- | -------- | --------------------------- |
| --accent       | #xxxxxx  | #xxxxxx  | bone 0.00 / surface 0.00    |
| --on-accent    | #xxxxxx  | #xxxxxx  | accent 0.00                 |
| --accent-soft  | #xxxxxx  | #xxxxxx  | ink 0.00                    |

実測値を書くのは、あとで色を触った人が「満たしているつもり」で壊さないためです。

6. 登録済みのプロダクト

共通ガイドに宣言されている製品 accent の一覧です。新しいプロダクトはここに 1 行足してから使い始めてください。

まだ登録されたプロダクトはありません。最初の 1 件を足すときに、下の形で行を作ってください。

プロダクトaccenton-accentaccent-softテーマ案件ガイド
プロダクト名#xxxxxx#xxxxxx#xxxxxxライト・ダークリポジトリ内のパス

明るさを揃える

2 つ目以降の accent は、1 つ目と --bone 上のコントラストを揃えてください（目安は 5〜7 の帯）。色相が違っても明度が揃っていれば、同じレイアウトに置いたときの重さが変わりません。案件ガイドには実測値を書いて、あとで色を触った人が「満たしているつもり」で壊さないようにします。

7. 共通への戻し方

案件で作ったものが 2 つ目のプロダクトでも要るようになったら、共通ガイドへ上げます。

  • 条件: 2 つ以上のプロダクトが同じ意味で使っている、または使う見込みがはっきりしている
  • 手順: 共通ガイドに節を足す PR を出す → 各案件ガイドの「共通との既知の差」から該当行を消す → 案件側の独自定義を共通トークンに置き換える
  • 順番を守る: 共通に入る前に他のプロダクトが真似すると、同じものに 2 つの名前が付きます
逆に、1 つのプロダクトでしか使わないものを共通ガイドに置かないでください。共通ガイドが大きくなるほど、新しいプロダクトが読む量が増えて守られなくなります。
